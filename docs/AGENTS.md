# docs/AGENTS.md —— 文档系统本身的用法

## 一、六层归宿表

| 层 | 路径 | 放什么 | 何时加载 |
|---|---|---|---|
| 常驻 | `AGENTS.md`（根） | 项目简介 + 五条铁律 + 文档索引（精简） | **总是** |
| 常驻·局部 | `docs/AGENTS.md` · `.superpowers/AGENTS.md` · `<package>/AGENTS.md` | 该处特有纪律 | agent `read`/`write`/`edit` 触达该目录后**自动** |
| 技能 | `.agents/skills/<name>/SKILL.md` | 可复用技术/纪律（**跨运行时**：Codex / Copilot CLI / Gemini CLI 也认） | 目录列出，按需 `skill()` |
| 决策记录 | `.agents/notes/{proposed,implemented,archived}/<分类>/YYYY-MM-DD-<slug>.md` | 为什么这么定、被谁取代 | 按索引读 |
| 长文 | `docs/agents/*.md` | 人读的纪律与调研长文 | 按索引读 |
| 机械强制 | `tools/gate.sh`（**待建**） | 门禁组合 / 验证脚本 / `git add` 白名单 | 直接跑 |

**一句话选层**：改代码前必读的规矩 → 根 `AGENTS.md`；某目录特有的纪律 → 该目录的 `AGENTS.md`；可复用的技术/流程 → `.agents/skills/`；
「为什么这么定、被谁取代」→ `.agents/notes/`；人读的纪律长文 → `docs/agents/`；**能机器拦的 → `tools/`（别只写文档）**。
★ 长文一律**不要用 `@` 导入**（导入会在启动时把文件展开进上下文，白载几千行）。

## 二、口径优先级（冲突时谁说了算）

1. **用户原话**（逐字收录在 `docs/agents/` 或 `docs/superpowers/specs/` 的「用户原话附录」）。
2. **最新落盘文档**（同主题多份时看后一份头部的「取代者」标注；冲突时以最新落盘为准）。
3. **根 `AGENTS.md`**（常驻精简口径）：与 `docs/agents/*.md` 长文冲突时**以根为准**（长文属留痕层）。
4. **上游参考**（DSH 官方源码/技能、TUI、dsh-web 的 README/issue）：是**事实来源**，不是本项目的裁定；转抄必须标注是否回核。
5. **旧文档 / 历史留痕**：只作溯源，**不作开工依据**；历史留痕一律不篡改。

★ 向用户提「待裁定」之前，**必须先做口径溯源并落盘**；已有裁定不得重复问。

## 三、文档间的「取代关系」怎么写

- 被取代的文档**不删**（历史留痕不改）。在**文件头部**加一行：
  `> **取代者：`docs/superpowers/specs/YYYY-MM-DD-<主题>.md`（YYYY-MM-DD）** —— 本文仅作历史留痕，**勿据此开工**。`
- 取代者一侧在标题下加一行：`> 本文取代：`<旧路径>`（YYYY-MM-DD）。`
- 只在**头部**写一次，不散落正文；被多次取代时列出全部路径（新的在前）。
- `.agents/notes/` 的决策记录同形制：`proposed/`（提议中，无约束力）→ `implemented/`（已落地）→ `archived/`（被取代，头部写 `取代者：`）。

## 四、`file:line` 与「生成命令」要求

- **现状事实必须给 `file:line`**（如 `~/.dsh/.agent-presets/liangshen/tool-bootstrap.mjs:111`），并注明是**回代码核过**还是**转抄**；转抄的标「未回核」。
- **跑过的结论必须给可复制的原命令 + 真实输出**（rc、计数、关键行原文）；**不许只写结论**，更不许把「没跑」写成「通过」。
- **数字要给生成命令**：测试计数 / 文件数 / 命中数 / 字节数，一律「命令 → 输出」成对出现，便于复核。
- 引用上游历史时给**取历史版本的命令**（如 `npm view <pkg>@<ver> dist.tarball` / GitHub `?ref=<tag>`）。
- 长输出不贴全文，给可复现命令 + 要点；报告/台账里必须留**未验证 / 没做**一节。

## 五、★ 日期口径规则

1. **引用用户原话时，日期取「用户实际说的那一天」**——不是文档落盘日、不是提交日。
2. **若与 git 提交日期矛盾，两者都记并标注疑点**：写成「用户口述 YYYY-MM-DD / 提交日期 YYYY-MM-DD（★ 日期疑点，两存）」，不许只留一个。
3. **不许用文件名反推日期**：仓库里可能存在文件名日期与内容日期不一致的文件；要日期就去正文找「用户原话 + 日期」，或看 `git log`，**并标注疑点**。
4. 文档里写「今天 / 本轮」时**带上绝对日期**；跨会话引用一律写绝对日期（`YYYY-MM-DD`）。

## 六、上游引用纪律（本项目特有）

- 本项目的关键事实大量来自**上游源码/README/issue**。写作时三分：① 本机回代码核过（给 `path:line` + md5/行数）；
  ② 上游一手文档/issue（给 URL + 日期，标「转抄」）；③ 二次转述（知乎 / 博客 / 视频 / 营销数字）——**只能当线索，不作验收依据**。
- 上游版本变化快（dsh-web 近期每天有 liangshen 提交）：引用必须带**版本或 commit**（如 `@linxin666/dsh-liangshen@0.4.6`、`dsh-web@32a12dfe`），
  不带版本的「上游说……了」一律视为无效引用。
